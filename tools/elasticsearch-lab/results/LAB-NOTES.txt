05-defaults.sh — needed 2 fixes (both caused by RPM security auto-config running during `docker build`)
1. TLS hostname: auto-config generates the HTTP cert in the build container, so its SANs are
   buildkitsandbox / localhost / 127.0.0.1 / ::1 / 172.17.0.2, not esd9/esd8. Every curl failed with
   "curl: (60) SSL: no alternative certificate subject name matches target host name 'esd9'".
   Fix (lib.sh): new curl_cmd helper used by e() and eq(): when /etc/elasticsearch/certs/ca.crt exists
   (our own certs, later phases) it connects to https://<node>:9200 as before; otherwise (auto-config
   http_ca.crt only) it connects to https://localhost:9200. Printed command lines in logs are unchanged.
2. Cluster never bootstrapped: auto-config wrote cluster.initial_master_nodes: ["buildkitsandbox"], but
   node.name defaults to the container hostname, so the node waited for a master forever;
   elasticsearch-reset-password exited 69 "Failed to determine the health of the cluster".
   Fix (05-defaults.sh): a logged step before first start replaces "buildkitsandbox" with $(hostname)
   (on a real host auto-config would have written the host's own name). In addition the reset tool
   connects to the publish address (container IP, not in SAN), so it now gets --url https://localhost:9200.
   The original elasticsearch.yml (with buildkitsandbox) is still printed unmodified earlier in the log.

40-lag.sh (es-prod esc1~esc3 + es-dr esd9 single-node follower, 30-day trial on both; final clean run 22:45; 3 runs)
Fix F7: the CCR lag metric. `_ccr/stats` leader_global_checkpoint is the leader checkpoint the follower LAST SAW,
  so Σ(leader_global_checkpoint - follower_global_checkpoint) stays 0 while the follower is cut off. In run 1
  B-3 the loop therefore ended at t=0 with "ops_behind=0" although follower had 500000 docs vs leader 550000.
  Now ops_behind = Σ leader primaries' seq_no.global_checkpoint (_cat/shards on esc1) - Σ follower_global_checkpoint
  (follower sampled first so the value is never negative; run 2 sampled leader first and got -2500..-3121
  during heavy writes). The stats-based value is still printed as ops_behind_stats for comparison.
  Also: _refresh on the follower before the final _count (run 2 showed 533364 although it held 550000), and the
  esd9 WARN grep is case-insensitive and matches ShardFollow (the old 'ccr|remote' pattern matched nothing).
Network-cut method: `docker network disconnect/connect --ip 192.168.60.41` worked; ES on esd9 kept its binding
  after reconnect (no pause_follow fallback needed).
