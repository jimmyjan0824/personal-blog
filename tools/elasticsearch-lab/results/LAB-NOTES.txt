05-defaults.sh — needed 2 fixes (both caused by RPM security auto-config running during `docker build`)
1. TLS hostname: auto-config generates the HTTP cert in the build container, so its SANs are
   buildkitsandbox / localhost / 127.0.0.1 / ::1 / 172.17.0.2, not esd9/esd8. Every curl failed with
   "curl: (60) SSL: no alternative certificate subject name matches target host name 'esd9'".
   Fix (lib.sh): new curl_cmd helper used by e() and eq(): when /etc/elasticsearch/certs/ca.crt exists
   (our own certs, later phases) it connects to https://<node>:9200 as before; otherwise (auto-config
   http_ca.crt only) it connects to https://localhost:9200. Printed command lines in logs are unchanged.
2. Cluster never bootstrapped: auto-config wrote cluster.initial_master_nodes: ["buildkitsandbox"], but
   node.name defaults to the container hostname, so the node waited for a master forever;
   elasticsearch-reset-password exited 69 "Failed to determine the health of the cluster".
   Fix (05-defaults.sh): a logged step before first start replaces "buildkitsandbox" with $(hostname)
   (on a real host auto-config would have written the host's own name). In addition the reset tool
   connects to the publish address (container IP, not in SAN), so it now gets --url https://localhost:9200.
   The original elasticsearch.yml (with buildkitsandbox) is still printed unmodified earlier in the log.
- After fixes: whole script ~47 s; no curl errors / 4xx in either log

Fixes (no conf/*.yml, *.yaml, heap or override values were changed)
F1. 10/20/30/40-*.sh were committed without the exec bit -> "permission denied"; chmod +x.
F2. compose.yaml: Docker Desktop gives containers RLIMIT_MEMLOCK = unlimited (not 8 MB as the compose
    comment assumed), and systemd 252 on Rocky 9 passes PID 1's limit to services, so mlockall succeeded
    without LimitMEMLOCK. Added `ulimits: { memlock: 8388608 }` to x-node to mimic a real Rocky 9 host
    (verified: without override the ES process gets 8 MiB soft/hard, with override unlimited).
F3. lib.sh curl_cmd: the phase-1 "connect to localhost" fallback broke when network.host is a specific IP
    (es1, esd8). Now verifies the cert as "localhost" but connects to the node via
    `--connect-to localhost:9200:<node>:9200` (only when the node still has the auto-config http_ca.crt).
F4. 10-single-node.sh
    - after 實測踩坑 1 and after every tryconf: `systemctl stop` before reset-failed. Otherwise a start that
      unexpectedly succeeds leaves ES running and all later `systemctl start` calls are no-ops (that is
      what happened on the first run: tryconf 2-4 all reported "active").
    - tryconf also prints the real reason (the Exception line after "fatal exception" in es-single.log);
      journalctl only shows the generic "Elasticsearch did not exit normally".
    - snap is a named volume and survives `compose rm`: clear /mnt/es-snapshots/single{,8} at start
      (2nd run failed with snapshot_name_already_in_use_exception for snap-1).
    - after `systemctl restart`: wait until health is green before the GET (immediately after restart the
      .security-7 shard is not yet available -> 503 "failed to retrieve password hash for reserved user").
    - thread_pool defaults query: dropped flat_settings=true (filter_path with dotted keys cannot match flat
      keys -> returned {}).
    - esd8 (8.19 with elasticsearch-single.yml, auto-config certs issued to buildkitsandbox):
      reset-password now uses `--url https://esd8:9200 -E xpack.security.http.ssl.verification_mode=certificate`;
      also prints the "unknown setting" line from es-single.log.
F5. 20-cluster.sh test 1: allocation explain now targets an UNASSIGNED orders replica (found via _cat/shards).
    Fixed shard 0 was sometimes on a surviving node ("current_state: started"); with no body ES picked a
    system index (.ds-ilm-history, default 1m delay) instead of orders (5m from the template).
