Redis 沒有 Schema，變更看起來很自由，但「自由」也代表沒有任何機制擋住錯誤的變更。本篇以 Redis 7.4 為主，整理各類變更的做法與回滾方案，最後整理升級到 8.x 的注意事項。

## 變更的分類

| 類型 | 例子 | 風險 | 回滾 |
| :--- | :--- | :--- | :--- |
| 動態參數 | `maxmemory`、`maxmemory-policy`、`slowlog-*` | 低 | `CONFIG SET` 改回 |
| 靜態參數（要重啟） | `io-threads`、`cluster-enabled`、`databases`、`bind` | 中 | 改回設定檔再重啟 |
| 版本升級 | 7.4.10 → 7.4.11、7.4 → 8.x | 中～高 | 小版本可降回；大版本受 RDB 格式限制 |
| Key 結構 | 改 key 名稱、改資料型別、拆大 key | 高 | 要事先設計雙寫或版本號 |
| Lua / Functions | 新增或修改腳本 | 中 | 保留舊版本 |
| 架構 | Standalone → Sentinel → Cluster | 高 | 舊架構保留到驗證完成 |

## 參數變更

```bash
# 1. 線上修改
redis-cli CONFIG SET maxmemory 12gb
# 2. 確認
redis-cli CONFIG GET maxmemory
# 3. 寫回設定檔（否則重啟就恢復原值）
redis-cli CONFIG REWRITE
```

- `CONFIG REWRITE` 會改寫 redis.conf，**保留原本的註解**，但被修改的參數會移到原本的位置或檔尾，並加上 `# Generated by CONFIG REWRITE` 區塊。Redis 對設定檔要有寫入權限。
- Sentinel 架構中，切換也會觸發 `CONFIG REWRITE`（改寫 `replicaof`），所以設定檔要納入版本控管時，要能接受 Redis 自己改寫。常見的做法是：版本控管的範本 + 部署工具產生的實際設定檔，比對時忽略 `replicaof` 與 Sentinel 自動產生的行。
- 主從架構的參數變更**每台都要做**，`CONFIG SET` 不會複製到從庫。
- 不能動態修改的參數用 `CONFIG SET` 會回 `ERR CONFIG SET failed ... can't set immutable config`。

## 滾動重啟

### Sentinel 架構

```text
1. 從庫逐台重啟：systemctl restart redis → 等 master_link_status:up 且 offset 追上
2. 計畫內切換：SENTINEL FAILOVER mymaster（讓一台已重啟的從庫成為主庫）
3. 重啟舊主庫（現在是從庫）
```

### Cluster 架構

```text
1. 每個分片先重啟從庫，等同步完成
2. 在從庫執行 CLUSTER FAILOVER，主從角色互換
3. 重啟舊主庫（現在是從庫）
4. 需要時再 CLUSTER FAILOVER 換回原本的分布
```

`CLUSTER FAILOVER`（不加參數）是安全的計畫內切換：主庫先停止接受寫入，等從庫追上 offset 才切換，**不會遺失資料**。

## 版本升級

### 7.4 小版本升級（例：7.4.10 → 7.4.11）

小版本只修 bug 與安全問題，持久化格式相同，可以直接替換執行檔滾動重啟：

```bash
cd /usr/local/src && curl -fsSLO https://download.redis.io/releases/redis-7.4.11.tar.gz
tar xzf redis-7.4.11.tar.gz && cd redis-7.4.11
make -j"$(nproc)" USE_SYSTEMD=yes && sudo make install
# 依上面的滾動重啟流程，逐台 systemctl restart redis
redis-cli INFO server | grep redis_version
```

### 升級到 8.x

| 步驟 | 內容 |
| :--- | :--- |
| 1. 閱讀 release notes | 8.0 到目標版本之間每一版的「Major changes」與設定變更 |
| 2. 測試環境驗證 | 應用程式完整跑一遍；特別注意 ACL、Lua 腳本、用戶端函式庫版本 |
| 3. 備份 | 在 7.4 上做一份 RDB 並異地保存（**這是唯一的回退依據**） |
| 4. 升從庫 | 新版只能當舊版的從庫，不能反過來 |
| 5. 切換 | `SENTINEL FAILOVER` / `CLUSTER FAILOVER`，新版成為主庫 |
| 6. 觀察 | 至少一個業務週期，確認延遲、記憶體、錯誤率 |
| 7. 升舊主庫 | 觀察期過後再升級，在那之前它是回退的退路 |

## Key 結構變更

Redis 沒有 `ALTER TABLE`，改 key 結構只能靠應用程式：

1. **新舊並存**：新版程式同時寫入新舊兩種 key（雙寫），讀取時先讀新 key，沒有再讀舊 key。
2. **背景搬遷**：用 `SCAN` 分批把舊 key 轉成新格式，每批之間休息，避免影響線上。
3. **切換讀取**：確認新 key 完整後，程式只讀新 key。
4. **清除舊 key**：用 `SCAN` + `UNLINK` 分批刪除，或讓舊 key 自然過期。

在 key 名稱中加上版本號（`user:v2:1001`）可以讓這個過程簡單很多。

## Lua 腳本與 Functions

- `EVAL` / `EVALSHA` 的腳本存在用戶端，`SCRIPT FLUSH` 或重啟後要重新載入（用戶端遇到 `NOSCRIPT` 要能自動重送）。
- 7.0 起的 **Functions**（`FUNCTION LOAD`）會持久化到 RDB / AOF 並複製到從庫，比較適合當作「資料庫端的程式」管理：

```bash
redis-cli -x FUNCTION LOAD REPLACE < order_lib.lua   # 以 library 為單位載入 / 取代
redis-cli FUNCTION LIST
redis-cli FUNCTION DUMP > functions-backup.bin       # 備份
```

- 腳本納入版本控管，部署時用 `FUNCTION LOAD REPLACE`，回滾就是載入上一版。

## 回滾方案

| 變更 | 回滾方式 |
| :--- | :--- |
| 動態參數 | `CONFIG SET` 改回 + `CONFIG REWRITE` |
| 靜態參數 | 改回設定檔，滾動重啟 |
| 7.4 小版本 | 換回舊執行檔，滾動重啟 |
| 7.4 → 8.x | 只要舊版從庫還在就切回去；否則用升級前的 RDB 還原（**會遺失升級後的寫入**） |
| Key 結構 | 雙寫期間切回讀舊 key |
| Functions | `FUNCTION LOAD REPLACE` 上一版，或 `FUNCTION RESTORE` 備份 |

## 版本差異比較：7.4 vs 8.x

升級到 8.x 時，以下變更可能影響既有的設定與流程：

| 項目 | 7.4.11 | 8.x（8.10.2） | 影響 |
| :--- | :--- | :--- | :--- |
| `io-threads-do-reads` | 有效 | 移除（設定檔裡有會被忽略） | 不需修改設定檔，但不會再有作用 |
| RDB 格式 | 12 | 8.6 起 13、14、15 | 8.6 以上無法降版 |
| 新增的保留指令 | — | `FT.*`、`JSON.*`、`TS.*`、`BF.*` 等（二進位版內建） | 若應用程式自訂了同名指令（極少見）會衝突 |
| ACL `+@all` | 不含模組指令 | 包含新模組指令 | 要重新檢視應用帳號的權限 |
| redis-cli `--cluster reshard` | `MIGRATE` | 8.10 起改用原子 slot 搬遷 | 搬遷流程與時間會不同 |
| 設定檔範本 | — | 多了 `redis-full.conf`（載入全部模組的版本） | 原始碼編譯時要決定用哪一份 |

### 給變更管理的升級建議

- 把每次升級需要的步驟寫成 Runbook，並先在測試環境照著做一遍。
- 升級期間凍結其他變更（參數、key 結構），出問題時才能快速判斷原因。
- 保留舊版從庫至少一個業務週期，這是唯一的無損回退方式。

## 小結

- `CONFIG SET` 之後記得 `CONFIG REWRITE`，而且每台都要做。
- 滾動重啟的順序：從庫 → 切換 → 舊主庫。`CLUSTER FAILOVER` 不會遺失資料。
- 大版本升級是單向的：新版只能當舊版的從庫，8.6 以上的 RDB 回不去 7.4。
- Key 結構變更靠雙寫與背景搬遷；腳本改用 Functions 管理。
