## 架構

| 主機 | IP | 角色 | 說明 |
| :--- | :--- | :--- | :--- |
| `esc1` | 192.168.60.21 | master + data + ingest | |
| `esc2` | 192.168.60.22 | master + data + ingest | |
| `esc3` | 192.168.60.23 | master + data + ingest | |
| `esc4` | 192.168.60.24 | data + ingest | 測試 6 擴充用，不是 master-eligible |
| `esd9` | 192.168.60.41 | 單節點叢集 `es-dr` | 測試 7 的 CCR follower |

- 三台都是 master-eligible，投票組態是 3 票、過半數是 2：**可以承受 1 台故障**，2 台同時故障就停止寫入（測試 3）。
- 每個索引 1 份副本，任何一台 data 節點故障都不會遺失資料。
- 規劃的主機規格和單節點相同：16 GB RAM、8 vCPU、本機 SSD。三台放在**不同的實體主機、不同的機架或電源**，否則 1 份副本保護不了什麼。

## 步驟 0：三台都做的 OS 與 systemd 設定

和[單節點]({% post_url 2026-10-24-elasticsearch-lab-01-single-node %})的步驟 0、1、3 完全相同：套用 `99-elasticsearch.conf`、用官方 RPM 套件庫安裝 `elasticsearch-9.5.5`、加上 `LimitMEMLOCK=infinity` 的 override。

**叢集和單節點最大的差別**：叢集沒有 `discovery.type: single-node`，所以 **bootstrap checks 全部強制執行**。單節點忘了 `LimitMEMLOCK` 只會留下 WARN，叢集節點則會拒絕啟動（`memory locking requested for elasticsearch process but memory is not locked`）。

防火牆（**未實測**）：9300 只開給叢集節點之間，9200 開給應用程式、Kibana 與監控：

```bash
sudo firewall-cmd --permanent --new-zone=es-transport && sudo firewall-cmd --reload
sudo firewall-cmd --permanent --zone=es-transport --add-source=192.168.60.21/32 --add-source=192.168.60.22/32 --add-source=192.168.60.23/32
sudo firewall-cmd --permanent --zone=es-transport --add-port=9300/tcp
sudo firewall-cmd --reload
```

## 步驟 1：自建 CA 與節點憑證

RPM 的 auto-config 在**每台主機各自**產生一個 CA，三台的 CA 互不信任，不能直接組成叢集。官方的做法是在第一台啟動後用 enrollment token 讓其他節點加入；這裡改用 `elasticsearch-certutil` 自建一個 CA、替每個節點簽發憑證，好處是憑證效期、SAN 都自己控制，加入新節點也不需要 token。

節點清單（SAN 要包含主機名、FQDN 與 IP，`verification_mode: full` 會驗證）：

```yaml
# elasticsearch-certutil cert --in 用的節點清單：SAN 包含主機名、FQDN 與 IP（verification_mode: full 會驗證主機名）
instances:
  - { name: esc1, dns: [ esc1, esc1.lab.local ], ip: [ 192.168.60.21 ] }
  - { name: esc2, dns: [ esc2, esc2.lab.local ], ip: [ 192.168.60.22 ] }
  - { name: esc3, dns: [ esc3, esc3.lab.local ], ip: [ 192.168.60.23 ] }
  - { name: esc4, dns: [ esc4, esc4.lab.local ], ip: [ 192.168.60.24 ] }
  - { name: esu1, dns: [ esu1, esu1.lab.local ], ip: [ 192.168.60.31 ] }
  - { name: esu2, dns: [ esu2, esu2.lab.local ], ip: [ 192.168.60.32 ] }
  - { name: esu3, dns: [ esu3, esu3.lab.local ], ip: [ 192.168.60.33 ] }
  - { name: esd9, dns: [ esd9, esd9.lab.local ], ip: [ 192.168.60.41 ] }
```

在任一台（這裡是 esc1）建立 CA 與所有節點的憑證：

- CA 10 年、節點憑證 825 天（約 27 個月）。**憑證到期是 Elasticsearch 叢集常見的大停機原因**，到期日要進監控（`GET _ssl/certificates`，見步驟 4）。
- `ca.key` 是整個叢集的信任根，簽完就移到離線的地方保管，**不要留在節點上**。
- `--pem` 產生 PEM 格式的憑證與私鑰，設定檔直接指定路徑，不需要在 keystore 放密碼。

### 每台節點：換掉 auto-config 的憑證

把 `node.crt`、`node.key`、`ca.crt` 放到每台的 `/etc/elasticsearch/certs/`（用 scp 或設定管理工具），同時刪掉 auto-config 的憑證與 keystore 裡對應的密碼：

```bash
cd /etc/elasticsearch
sudo rm -f certs/http_ca.crt certs/http.p12 certs/transport.p12
for k in xpack.security.http.ssl.keystore.secure_password \
         xpack.security.transport.ssl.keystore.secure_password \
         xpack.security.transport.ssl.truststore.secure_password; do
  sudo /usr/share/elasticsearch/bin/elasticsearch-keystore remove $k
done
sudo install -o root -g elasticsearch -m 640 esc1.crt certs/node.crt
sudo install -o root -g elasticsearch -m 640 esc1.key certs/node.key
sudo install -o root -g elasticsearch -m 644 ca.crt   certs/ca.crt
```

```console
[esc1]# /usr/share/elasticsearch/bin/elasticsearch-keystore list | tr '\n' ' '; echo; ls /etc/elasticsearch/certs
autoconfiguration.password_hash cluster.state.encryption.active_password_id cluster.state.encryption.password.autoconfigured keystore.seed 
ca.crt
node.crt
node.key
```

- keystore 只留 `cluster.state.encryption.*`（9.5 的叢集狀態加密，**不要刪**）、`keystore.seed` 與 `autoconfiguration.password_hash`。
- 留著不用的 `*.secure_password` 不會讓啟動失敗，但會讓人搞不清楚現在用的是哪一組憑證，一起清掉。

## 步驟 2：設定檔

### elasticsearch.yml

三台共用同一份，只有 `node.name` 與 `network.host` 不同。標記方式和單節點相同（建議 / 預設 / 必要），叢集多了 discovery、故障偵測、分配與 TLS 的部分：

```yaml
# /etc/elasticsearch/elasticsearch.yml
# Elasticsearch 9.5 三節點叢集（esc1~esc3 共用，只有 node.name、network.host 不同）：效能與運維設定
# 以「16 GB RAM、8 vCPU、本機 SSD、專用 Elasticsearch 主機，三台都是 master + data + ingest」為基準。
# 每個參數上一行的註解：
#   建議：調整過的值（括號內是預設值）
#   預設：9.5.5 的預設值（在全新安裝的 9.5.5 上用 GET _cluster/settings?include_defaults 逐一核對過），
#         寫出來是為了讓設定一目了然，日後要調整時知道從哪裡開始
#   必要：名稱、路徑、位址、憑證等依環境而定、沒有好壞之分的值
# 「動態」表示也可以用 PUT _cluster/settings 線上調整（persistent 會蓋過這個檔案），其他的改了要滾動重啟。
# 索引層級的參數（refresh、translog、merge、慢日誌等）不能寫在這裡，放在索引範本 index-template.yaml。

#------------------------------------------------------------------------------
# 叢集與節點
#------------------------------------------------------------------------------
# 必要（預設 elasticsearch）。同一個網段的叢集名稱不要重複，日誌檔名也用它（/var/log/elasticsearch/es-prod.log）
cluster.name: es-prod
# 必要（預設 = 主機名）。cluster.initial_master_nodes 要寫一模一樣的名稱
node.name: esc1
# 建議（預設是所有角色：master、data 與各 data tier、ingest、ml、transform、remote_cluster_client）。
# 小型叢集三台都是 master + data + ingest；不用機器學習就不要給 ml（它會另外啟動原生行程、吃記憶體），
# 要跨叢集搜尋 / CCR 再加 remote_cluster_client
node.roles: [ master, data, ingest ]
# 預設是不設定（只在跨機房 / 機架時才要）。設了之後配合下方的 awareness，主分片與副本會分散到不同 zone
#node.attr.zone: zone-a

#------------------------------------------------------------------------------
# 路徑
#------------------------------------------------------------------------------
# 必要（RPM 預設）。本機 SSD；不要放 NFS。多顆磁碟用 RAID 0 / LVM 合成一個路徑（多個 path.data 已棄用）
path.data: /var/lib/elasticsearch
# 必要（RPM 預設）
path.logs: /var/log/elasticsearch
# 建議（預設空）。fs 快照儲存庫的根目錄，所有 master 與 data 節點都要掛載同一個共用路徑（NFS）
path.repo: [ "/mnt/es-snapshots" ]

#------------------------------------------------------------------------------
# 記憶體
#------------------------------------------------------------------------------
# 建議（預設 false）。啟動時把 heap 鎖在記憶體裡，不會被 swap 出去；
# 需要 systemd 的 LimitMEMLOCK=infinity（override.conf），否則 bootstrap check 失敗、拒絕啟動
# （多節點叢集才會；single-node 只會記一筆 WARN）
bootstrap.memory_lock: true

#------------------------------------------------------------------------------
# 網路
#------------------------------------------------------------------------------
# 建議（預設 _local_ = 只聽 loopback）。綁內網 IP；綁了非 loopback 位址就進入「正式模式」，bootstrap checks 全部強制執行
network.host: 192.168.60.21
# 建議（預設 9200-9300 = 從 9200 起找第一個可用的 port）。固定下來，避免同一台誤啟動第二個行程時悄悄綁到 9201
http.port: 9200
# 建議（預設 9300-9399）。同上，防火牆規則也比較好寫
transport.port: 9300
# 預設。單一 HTTP 請求（含 bulk）的上限，超過回 413；bulk 每批 5～15 MB 就夠了，不要調大
http.max_content_length: 100mb
# 預設（啟用 HTTPS 時預設 false）。TLS 上做壓縮有 BREACH 類攻擊的風險，維持關閉
http.compression: false
# 預設。節點之間只壓縮寫入資料（bulk 轉送給副本、復原），其他訊息不壓縮
transport.compress: indexing_data
# 預設
transport.compression_scheme: lz4
# 預設。TCP keepalive，搭配 OS 的 net.ipv4.tcp_keepalive_* 偵測半斷線的連線
network.tcp.keep_alive: true
# 預設（-1 = 用 OS 設定，Rocky 9 是 7200 秒）。前面有會切斷閒置連線的防火牆 / LB 時，設得比它的逾時短
network.tcp.keep_idle: -1
# 預設
network.tcp.no_delay: true

#------------------------------------------------------------------------------
# 叢集組成（discovery）與故障偵測
#------------------------------------------------------------------------------
# 必要（預設空）。所有 master-eligible 節點的位址（port 預設 9300）。新節點靠它找到叢集
discovery.seed_hosts: [ "esc1", "esc2", "esc3" ]
# 必要，只在叢集「第一次」啟動時使用：列出初始的 master-eligible 節點（要和 node.name 相同）。
# 叢集組成後一定要移除這一行（滾動重啟時拿掉），否則資料目錄被清空的節點可能自己 bootstrap 出新的叢集
cluster.initial_master_nodes: [ "esc1", "esc2", "esc3" ]
# 預設。master 每秒檢查每個節點一次
cluster.fault_detection.follower_check.interval: 1s
# 預設。單次檢查的逾時
cluster.fault_detection.follower_check.timeout: 10s
# 預設。連續失敗 3 次就把節點移出叢集（最長約 30 秒）；GC 暫停常常超過這個時間時，先解決 heap 問題，不要調大
cluster.fault_detection.follower_check.retry_count: 3
# 預設。其他節點檢查 master 是否還在
cluster.fault_detection.leader_check.interval: 1s
# 預設
cluster.fault_detection.leader_check.timeout: 10s
# 預設
cluster.fault_detection.leader_check.retry_count: 3
# 預設。master 發布一次叢集狀態的逾時；常常逾時代表叢集狀態太大（分片、欄位太多）
cluster.publish.timeout: 30s
# 預設。沒有 master 時拒絕寫入、仍允許讀取（all = 讀寫都拒絕）
cluster.no_master_block: write
# 預設。節點離開時自動調整投票組態，維持奇數個投票者
cluster.auto_shrink_voting_configuration: true

#------------------------------------------------------------------------------
# 分片分配與復原（全部是動態）
#------------------------------------------------------------------------------
# 預設。all / primaries / new_primaries / none；滾動重啟時暫時改成 primaries
cluster.routing.allocation.enable: all
# 預設。always / indices_primaries_active / indices_all_active
cluster.routing.allocation.allow_rebalance: always
# 預設
cluster.routing.rebalance.enable: all
# 預設。整個叢集同時進行的分片搬移數
cluster.routing.allocation.cluster_concurrent_rebalance: 2
# 預設。每個節點同時進行的復原數（進、出各自計算）
cluster.routing.allocation.node_concurrent_recoveries: 2
# 預設。節點重啟後，每個節點同時從本機資料復原的主分片數
cluster.routing.allocation.node_initial_primaries_recoveries: 4
# 預設。同一台實體主機跑多個節點時才要改 true（避免主分片與副本落在同一台主機）
cluster.routing.allocation.same_shard.host: false
# 預設是不設定。跨 zone 時取消註解，配合 node.attr.zone
#cluster.routing.allocation.awareness.attributes: [ zone ]
# 預設（每個節點）。SSD + 10GbE 的環境，離峰時可以用 PUT _cluster/settings 暫時調到 200mb 加快復原 / 搬移
indices.recovery.max_bytes_per_sec: 40mb
# 預設。每個復原同時傳送的檔案區塊數
indices.recovery.max_concurrent_file_chunks: 2
# 預設。每個復原同時重播的 translog 操作批次數
indices.recovery.max_concurrent_operations: 1
# 預設。依 replica selection 選擇回應最快的分片副本處理搜尋
cluster.routing.use_adaptive_replica_selection: true
# 預設。每個非 frozen 的 data 節點最多 1000 個分片（含副本），超過就不能再建索引；碰到時應該減少分片，不要調高
cluster.max_shards_per_node: 1000

#------------------------------------------------------------------------------
# 磁碟水位（全部是動態）
#------------------------------------------------------------------------------
# 預設
cluster.routing.allocation.disk.threshold_enabled: true
# 預設。超過就不再把「副本」分配到這個節點；告警要設在這之前（例如 80%）
cluster.routing.allocation.disk.watermark.low: 85%
# 預設。大磁碟時改用「剩餘空間」判斷：剩餘 200GB 以下才算超過低水位
cluster.routing.allocation.disk.watermark.low.max_headroom: 200GB
# 預設。超過就開始把分片搬離這個節點
cluster.routing.allocation.disk.watermark.high: 90%
# 預設
cluster.routing.allocation.disk.watermark.high.max_headroom: 150GB
# 預設。超過就把這個節點上的索引全部設成唯讀（read_only_allow_delete），寫入全部失敗
cluster.routing.allocation.disk.watermark.flood_stage: 95%
# 預設
cluster.routing.allocation.disk.watermark.flood_stage.max_headroom: 100GB
# 預設。多久收集一次各節點的磁碟用量
cluster.info.update.interval: 30s

#------------------------------------------------------------------------------
# 寫入緩衝與背壓
#------------------------------------------------------------------------------
# 預設。所有分片共用的寫入緩衝區（heap 的比例），寫入非常重的節點可以調到 15%～20%，需重啟
indices.memory.index_buffer_size: 10%
# 預設
indices.memory.min_index_buffer_size: 48mb
# 預設（heap 的 10%）。正在處理中的寫入資料超過這個量就回 429，保護 heap，需重啟
indexing_pressure.memory.limit: 10%

#------------------------------------------------------------------------------
# 快取
#------------------------------------------------------------------------------
# 預設（heap 的 10%）。filter 子句的結果快取，需重啟
indices.queries.cache.size: 10%
# 預設（heap 的 1%）。size: 0 的查詢（聚合）結果快取，refresh 後失效，需重啟
indices.requests.cache.size: 1%
# 建議（預設 -1 = 無上限，只受 fielddata 斷路器 40% 限制）。設上限讓舊的 fielddata 被淘汰，而不是讓查詢一直被斷路器拒絕；
# 正確的做法是不要在 text 欄位上開 fielddata，這只是保險，需重啟
indices.fielddata.cache.size: 20%

#------------------------------------------------------------------------------
# 斷路器（動態）
#------------------------------------------------------------------------------
# 預設。依 JVM 實際的 heap 用量判斷（需重啟才能改）
indices.breaker.total.use_real_memory: true
# 預設（use_real_memory 為 true 時是 95%）。所有斷路器加總的上限
indices.breaker.total.limit: 95%
# 預設
indices.breaker.fielddata.limit: 40%
# 預設。單一請求（聚合等）可用的 heap
indices.breaker.request.limit: 60%
# 預設。傳輸中的請求（HTTP、transport）可用的 heap
network.breaker.inflight_requests.limit: 100%

#------------------------------------------------------------------------------
# 執行緒池（需重啟）
#------------------------------------------------------------------------------
# 執行緒數依 CPU 自動計算（write = CPU 數、search = CPU × 3 / 2 + 1），不要手動設 size。
# 預設是偵測到的 CPU 數；容器限制了 CPU 而 JVM 偵測錯誤時才要設
#node.processors: 8
# 預設。佇列滿了回 429（rejected）；調大佇列只會讓延遲變高，不會增加處理能力
thread_pool.write.queue_size: 10000
# 預設（9.x；8.19 是 1000）
thread_pool.search.queue_size: 16000

#------------------------------------------------------------------------------
# 搜尋保護（動態）
#------------------------------------------------------------------------------
# 預設。單一查詢的聚合 bucket 上限
search.max_buckets: 65536
# 預設（-1 = 不限制）。全域的查詢逾時；各查詢可以自己帶 timeout
search.default_search_timeout: -1
```

| 參數 | 單節點 | 叢集 | 為什麼 |
| :--- | :--- | :--- | :--- |
| `discovery.type` | `single-node` | 不設定（multi-node） | 叢集靠 `seed_hosts` 互相找到對方 |

| `cluster.fault_detection.*`、`cluster.publish.timeout` | — | 預設 | 決定故障偵測要多久（測試 1、2） |

### 索引範本

和單節點的差別只有兩個參數：`number_of_replicas` 回到預設的 1，並把 `index.unassigned.node_left.delayed_timeout` 從 1 分鐘調成 5 分鐘：

```yaml
# PUT _component_template/base-settings（Content-Type: application/yaml，註解會被忽略）
# 索引層級的效能與運維設定：elasticsearch.yml 不能放索引設定，統一用 component template 套到所有業務索引。
# 以「三節點叢集、業務資料（非日誌）、搜尋與寫入並重」為基準。
# 標記規則和 elasticsearch.yml 相同：建議 = 調整過的值（括號內是預設值）；預設 = 9.5.5 的預設值
# （在全新的 9.5.5 上用 GET <index>/_settings?include_defaults 逐一核對過）。
# 「動態」表示建立後也可以 PUT <index>/_settings 修改；其他的只在建立索引時生效。
version: 1
_meta:
  description: "base index settings for business indices (es-prod)"
template:
  settings:
    #--------------------------------------------------------------------------
    # 分片與副本
    #--------------------------------------------------------------------------
    # 預設。主分片數建立後不能改（只能 split / shrink / reindex）；每個分片 10～50 GB，預估會超過再在建立時指定
    index.number_of_shards: 1
    # 預設，動態。1 份副本可承受 1 台 data 節點故障
    index.number_of_replicas: 1
    # 預設，動態。不要自動依節點數調整副本（auto_expand_replicas 會忽略部分分配規則）
    index.auto_expand_replicas: false
    # 建議（預設 1m），動態。節點離開後等 5 分鐘才在其他節點重建副本：重開機、滾動重啟不必整份重新複製
    index.unassigned.node_left.delayed_timeout: 5m
    # 預設，動態（-1 = 不限制）。熱點索引的分片擠在同一台時，設成「主分片數 × (1 + 副本數) ÷ 節點數」再加 1
    index.routing.allocation.total_shards_per_node: -1
    # 預設，動態。寫入前只要求主分片 active；設 all 會在副本不在時拒絕寫入（可用性下降）
    index.write.wait_for_active_shards: 1
    # 預設，動態。分片分配失敗的重試次數，用完要 POST _cluster/reroute?retry_failed=true
    index.allocation.max_retries: 5

    #--------------------------------------------------------------------------
    # refresh 與 translog
    #--------------------------------------------------------------------------
    # 預設是不設定（= 1s，而且索引閒置 index.search.idle.after 後暫停 refresh，下一次搜尋時才 refresh）。
    # 明確寫 1s 會關掉 search idle 的行為；日誌類資料建議 30s；大量匯入時暫時設 -1
    #index.refresh_interval: 1s
    # 預設，動態。沒設 refresh_interval 的索引，30 秒沒有搜尋就暫停定期 refresh
    index.search.idle.after: 30s
    # 預設，動態。每個寫入請求回應前都把 translog fsync 到磁碟；async 會在當機時遺失最多 sync_interval 的資料
    index.translog.durability: request
    # 預設，動態。durability 為 async 時的 fsync 間隔（也是 request 模式下背景 fsync 的間隔）
    index.translog.sync_interval: 5s
    # 預設，動態。translog 累積到這個大小就 flush（Lucene commit）
    index.translog.flush_threshold_size: 10gb
    # 預設，動態。距離上次 flush 超過這個時間也會 flush
    index.translog.flush_threshold_age: 1m

    #--------------------------------------------------------------------------
    # merge 與儲存（9.x 調整過 merge policy 的預設值，8.19 的值見文章）
    #--------------------------------------------------------------------------
    # 預設。default = LZ4；日誌、歸檔類索引建議 best_compression（DEFLATE，省 15%～25% 空間、寫入稍慢），建立時才能設
    index.codec: default
    # 預設，動態。小於這個大小的 segment 一律視為這個大小來挑選合併對象（8.19 是 2mb）
    index.merge.policy.floor_segment: 16mb
    # 預設，動態。每一層允許的 segment 數（8.19 是 10.0）
    index.merge.policy.segments_per_tier: 8.0
    # 預設，動態。一次合併最多幾個 segment（8.19 是 10）
    index.merge.policy.max_merge_at_once: 16
    # 預設，動態。已刪除文件超過 segment 的 20% 時優先合併
    index.merge.policy.deletes_pct_allowed: 20.0
    # 預設，動態。merge 太多時自動降低寫入的 merge 速度，避免 I/O 被 merge 吃光
    index.merge.scheduler.auto_throttle: true
    # 預設。啟動時不檢查分片檔案（checksum 會讓大分片啟動很慢；懷疑損毀時才暫時設 checksum）
    index.shard.check_on_startup: false

    #--------------------------------------------------------------------------
    # mapping 保護（動態）
    #--------------------------------------------------------------------------
    # 預設。欄位總數上限（含 multi-field、object）；超過代表 mapping 設計有問題（mapping explosion），不要隨便調高
    index.mapping.total_fields.limit: 1000
    # 預設。物件巢狀深度上限
    index.mapping.depth.limit: 20
    # 預設（9.x；8.19 是 50）。nested 欄位數上限
    index.mapping.nested_fields.limit: 100
    # 預設。單一文件中 nested 物件總數上限
    index.mapping.nested_objects.limit: 10000
    # 預設。不自動轉型（"5" 不會被當成數字 5 寫進 integer 欄位）
    index.mapping.coerce: false
    # 預設。格式錯誤的值讓整份文件寫入失敗，而不是悄悄忽略
    index.mapping.ignore_malformed: false

    #--------------------------------------------------------------------------
    # 查詢保護與快取（動態）
    #--------------------------------------------------------------------------
    # 預設。from + size 的上限；深分頁用 search_after + PIT，不要調高
    index.max_result_window: 10000
    # 預設。inner_hits、top_hits 的 from + size 上限
    index.max_inner_result_window: 100
    # 預設。terms 查詢的詞數上限
    index.max_terms_count: 65536
    # 預設。regexp 查詢的長度上限
    index.max_regex_length: 1000
    # 預設。refresh=wait_for 同時等待的請求上限，超過的請求會被強制 refresh
    index.max_refresh_listeners: 1000
    # 預設。node query cache（filter 結果）
    index.queries.cache.enabled: true
    # 預設。shard request cache（size: 0 的聚合結果）
    index.requests.cache.enable: true

    #--------------------------------------------------------------------------
    # 慢日誌（預設全部 -1 = 關閉；寫到 /var/log/elasticsearch/<cluster.name>_index_*_slowlog.json）
    #--------------------------------------------------------------------------
    # 建議（預設 -1），動態。查詢階段超過 5 秒記 WARN
    index.search.slowlog.threshold.query.warn: 5s
    # 建議（預設 -1），動態
    index.search.slowlog.threshold.query.info: 2s
    # 建議（預設 -1），動態。fetch 階段（取回 _source）
    index.search.slowlog.threshold.fetch.warn: 1s
    # 建議（預設 -1），動態
    index.search.slowlog.threshold.fetch.info: 500ms
    # 建議（預設 false），動態。記錄是哪個使用者 / API key 發出的查詢
    index.search.slowlog.include.user: true
    # 建議（預設 -1），動態
    index.indexing.slowlog.threshold.index.warn: 5s
    # 建議（預設 -1），動態
    index.indexing.slowlog.threshold.index.info: 2s
    # 預設，動態。慢寫入日誌記錄 _source 的前 1000 個字元
    index.indexing.slowlog.source: 1000
    # 建議（預設 false），動態
    index.indexing.slowlog.include.user: true
```

`delayed_timeout: 5m` 的效果在測試 1 會看到：節點離開後，副本**不會馬上**在其他節點重建（那要整份複製），而是等 5 分鐘；重開機、滾動重啟通常在 5 分鐘內回來，回來後只要補上差異。

## 測試 7：同步落後

「同步落後」在 Elasticsearch 有兩種，概念見[監控與告警]({% post_url 2026-10-24-elasticsearch-ops-04-monitoring %})的「同步落後怎麼看」，這裡實際量測。這一節由 `40-lag.sh` 執行：重新建一個同樣設定的 `es-prod`（esc1～esc3），另外用 esd9 建一個單節點的 `es-dr` 叢集當 CCR 的 follower。

### 7-1 叢集內副本：正常狀態

叢集內的副本是**同步**複製：寫入要等所有 in-sync 副本都完成才回應。所以正常狀態下，同一個分片的主分片與副本，`seq_no.max`、`local_checkpoint`、`global_checkpoint` 三個值完全相同：

```console
[esc1] GET /_cat/shards/orders?v&h=shard,prirep,state,node,docs,seq_no.max,seq_no.local_checkpoint,seq_no.global_checkpoint&s=shard,prirep
shard prirep state   node  docs seq_no.max seq_no.local_checkpoint seq_no.global_checkpoint
0     p      STARTED esc2 23501      33583                   33583                    33583
0     r      STARTED esc1 23501      33583                   33583                    33583
1     p      STARTED esc1 23167      33086                   33086                    33086
1     r      STARTED esc3 23246      33086                   33086                    33086
2     p      STARTED esc3 21629      33328                   33328                    33328
2     r      STARTED esc2 21629      33328                   33328                    33328
```

- 三個分片的 `seq_no.max` 加起來約 10 萬，就是寫入的操作數；`docs` 加起來只有 6.8 萬，是因為最後幾批還沒 refresh（`_cat/shards` 的 `docs` 只算已經 refresh、搜得到的文件）。

把 follower 的讀取限制在每次 500 筆、同時只有 1 個讀取請求（預設是 5120 筆、12 個），在 leader 寫入 20 萬筆，每 2 秒取樣：

把 esd9 從網路上拔掉（`docker network disconnect`），leader 寫入 5 萬筆、等 20 秒，再接回去：


- 網路恢復後 **5 秒內**追上 5 萬個操作，不需要任何人工操作：follower 會自己重試，leader 也用 retention lease 保留了這些操作。
- 斷線期間如果只看 `_ccr/stats`，落後量**一直是 0**（`leader_global_checkpoint` 停在斷線前的值）。第一版腳本就是這樣算的，結果網路還沒接回、迴圈就以為已經追上而結束了。
- **三次實測中有一次，一個分片卡了約 200 秒**：另外兩個分片 5 秒內追上，shard 1 停在落後 16636 個操作，到 t=207 秒才繼續，同時出現上面那行 retention lease 的 WARN（推測是斷線時送出的讀取請求一直等到逾時才重試）。所以監控 CCR 落後要**逐個分片**看，不能只看加總；網路恢復後幾分鐘內沒有追上，先看 follower 日誌的 `ShardFollowTasksExecutor`，必要時 `pause_follow` / `resume_follow` 重新開始讀取（實測沒有用到）。
- follower 離線的時間如果超過 leader 的 retention lease 期限（預設 12 小時），leader 的歷史操作會被清掉，follower 會出現 `fatal_exception`，只能刪掉重建。

## 實測踩到的坑

| 現象 | 原因 | 解法 |
| :--- | :--- | :--- |
| 三台各自用 auto-config 的憑證，無法組成叢集 | 每台的 auto-config 各自產生 CA，互不信任 | 自建 CA（本文）或用 enrollment token 加入 |
| 失去過半數時，健康檢查回 401 而不是 503 | `.security` 只有 1 主 1 副本，存活節點上沒有任何一份，連 `elastic` 都無法驗證 | 監控同時檢查節點數與 master；必要時用 file realm 的帳號做監控 |
| 失去過半數時 `_count` 回 200 但數字少了三分之一 | 沒有 master 時讀取照常，只回答本機分片 | 應用程式檢查 `_shards.failed` |
| master 無回應時，新 master 約 63 秒才生效 | 選舉後的第一次發布要等 `cluster.publish.timeout`（30 秒）等被凍結的舊 master | 規劃 RTO 時以 1 分鐘估算；不建議為此調低 publish timeout |
| 重啟後一直有 `this node is locked into cluster UUID ... remove this setting` | `cluster.initial_master_nodes` 沒有移除 | 叢集組成後，下一次滾動重啟時移除 |
| `allocation explain` 不帶參數時解釋的是系統索引 | 不帶 body 時解釋它找到的第一個未分配分片 | 指定 `index`、`shard`、`primary` |
| CCR 斷線期間 `_ccr/stats` 算出的落後一直是 0 | `leader_global_checkpoint` 是 follower 上次讀到的值 | 用 leader 叢集主分片的 `seq_no.global_checkpoint` 計算 |
| 網路恢復後 CCR 有一個分片停了約 200 秒 | 斷線時送出的讀取請求要等到失敗才重試 | 逐個分片監控；必要時 `pause_follow` / `resume_follow` |
| 系統索引的副本 1 分鐘就重建，業務索引要等 5 分鐘 | 系統索引不套用我們的範本 | 預期行為；系統索引很小，重建很快 |

## 驗證方式與結果

驗證環境、建置檔與 `compose.yaml` 和[單節點]({% post_url 2026-10-24-elasticsearch-lab-01-single-node %})相同（esc1～esc4 使用已安裝 9.5.5 的 `eslab-rocky9-es9` 映像）。執行 `./20-cluster.sh`（同步落後是 `./40-lag.sh`），輸出記錄在 `results/`。故障是在主機端用 `docker compose pause` / `unpause` 製造的：容器整個凍結，行程不會結束、TCP 連線不會斷，等同於主機當掉或嚴重的 GC 暫停。

`20-cluster.sh` 完整跑了三次，表格中的時間是三次的範圍：

| 測試 | 怎麼驗證 | 判定通過的條件 | 結果 |
| :--- | :--- | :--- | :--- |
| 憑證 | `openssl x509`、`_ssl/certificates` | SAN 含主機名與 IP、`verification_mode: full` 可以組成叢集 | ✅ |

## 小結

- 三節點都是 master-eligible，可以承受 1 台故障；用自建 CA 簽發含正確 SAN 的憑證，transport 層用 `verification_mode: full`。
- 第一次啟動三台同時起來，叢集組成後下一次滾動重啟時移除 `cluster.initial_master_nodes`。
- 主機無回應時，data 節點約 **33 秒**被移除；master 無回應時新 master 約 **33～63 秒**才生效。應用程式的逾時與重試要涵蓋這段時間。
- `delayed_timeout: 5m` 讓短暫離線的節點回來後只補差異，不必整份複製。
- 失去過半數時拒絕寫入，但讀取可能回傳部分結果、驗證可能失敗；**救回節點就會自動恢復**，不要輕易 `unsafe-bootstrap`。
- 滾動重啟的關鍵：`allocation.enable: primaries`、master 最後做、做完把 `persistent` 清乾淨。
- 叢集內的副本是同步複製，看 `seq_no` 與 checkpoint；跨叢集的 CCR 是非同步的，落後量用 `_ccr/stats` 的 global checkpoint 差距監控。
